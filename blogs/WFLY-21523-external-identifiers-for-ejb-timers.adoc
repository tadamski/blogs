Process automation managers and long-running workflow engines often need to query EJB timers based on custom business metadata. While it has always been possible to store this metadata in the `Serializable` info object passed to `TimerConfig`, querying timers this way is highly inefficient — the timer service must deserialize each timer's info object sequentially, one by one, until it finds a match.

https://issues.redhat.com/browse/WFLY-21523[WFLY-21523] solves this by introducing an indexed `external_id` column in the timer persistence schema and exposing an extended Java API to configure and query it. Applications can now tag timers with a specific business key upon creation, enabling low-latency SQL lookups directly through the EJB Timer Service.

== How to use it

The feature is opt-in and fully backward compatible. It introduces two new classes in the `org.jboss.ejb3.timerservice` package (part of the public `org.jboss.ejb3` module automatically available to all EJB deployments):

* `ExtendedTimerConfig` — extends `jakarta.ejb.TimerConfig` with an `externalId` property
* `ExtendedTimerService` — extends `jakarta.ejb.TimerService` with a `getTimersByExternalId(String externalId)` method

=== Creating a timer with an external ID

[source,java]
----
@Singleton
public class WorkflowEngine {
    @Resource
    private TimerService timerService;

    public void scheduleTask(String processInstanceId, Date deadline) {
        ExtendedTimerConfig config = new ExtendedTimerConfig();
        config.setExternalId(processInstanceId);
        config.setPersistent(true);

        timerService.createSingleActionTimer(deadline, config);
    }
}
----

=== Querying timers by external ID

[source,java]
----
@Singleton
public class WorkflowEngine {
    @Resource
    private TimerService timerService;

    public Collection<Timer> findTimersByProcessInstance(String processInstanceId) {
        ExtendedTimerService extendedService = (ExtendedTimerService) timerService;
        return extendedService.getTimersByExternalId(processInstanceId);
    }
}
----

The query is backed by an indexed `SELECT` statement on the `EXTERNAL_ID` column, making it fast even with thousands of active timers.

== Backward compatibility

The `EXTERNAL_ID` column is nullable. On first startup after upgrade, `DatabaseTimerPersistence` detects if the column is missing and automatically executes an `ALTER TABLE` to migrate existing tables. Existing applications using standard `TimerConfig` objects continue to work unchanged — the external ID defaults to `NULL` and the new capabilities are completely opt-in.

== Under the hood

The implementation spans the public API library (`jboss-ejb3-ext-api`) and the EJB3 subsystem. `DatabaseTimerPersistence` now includes `EXTERNAL_ID` in all `INSERT`, `UPDATE`, and `SELECT` statements and implements `loadActiveTimersByExternalId` using a `PreparedStatement` that filters by the new column. `TimerServiceImpl` checks both active in-memory timers and uncommitted transaction timers before delegating to the persistence layer, guaranteeing a complete and accurate result set.
