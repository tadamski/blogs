Workflow engines and process automation frameworks, such as jBPM, often need to find timers by custom business metadata. It has always been possible to store that metadata in the `Serializable` info object you pass to `TimerConfig`. But querying timers that way is slow: the timer service has to deserialize each timer's info object, one by one, until it finds a match.

WildFly 43 adds an _external identifier_ to persistent timers. It is stored in its own indexed database column and exposed through a small extension of the timer API. You can tag a timer with a business key when you create it, and later find it with a fast SQL lookup through the Jakarta Enterprise Beans Timer Service.

== How to use it

The feature is opt-in. It adds two classes to the `org.jboss.ejb3.timerservice` package, which is provided by the `jboss-ejb3-ext-api` library that is part of WildFly and visible to all Jakarta Enterprise Beans deployments:

* `ExtendedTimerConfig` extends `jakarta.ejb.TimerConfig` with an `externalId` property.
* `ExtendedTimerService` extends `jakarta.ejb.TimerService` with a `getTimersByExternalId(String externalId)` method.

To compile against them, add the library to your build with the `provided` scope, using the version shipped with the server:

[source,xml]
----
<dependency>
    <groupId>org.jboss.ejb3</groupId>
    <artifactId>jboss-ejb3-ext-api</artifactId>
    <scope>provided</scope>
</dependency>
----

=== Creating a timer with an external identifier

[source,java]
----
@Singleton
public class WorkflowEngine {
    @Resource
    private TimerService timerService;

    public void scheduleTask(String processInstanceId, Date deadline) {
        ExtendedTimerConfig config = new ExtendedTimerConfig();
        config.setExternalId(processInstanceId);
        config.setPersistent(true);

        timerService.createSingleActionTimer(deadline, config);
    }
}
----

=== Querying timers by external identifier

[source,java]
----
@Singleton
public class WorkflowEngine {
    @Resource
    private TimerService timerService;

    public Collection<Timer> findTimersByProcessInstance(String processInstanceId) {
        ExtendedTimerService extendedService = (ExtendedTimerService) timerService;
        return extendedService.getTimersByExternalId(processInstanceId);
    }
}
----

The lookup is an indexed `SELECT` on the `EXTERNAL_ID` column, so it stays fast even with thousands of active timers. The identifier doesn't have to be unique: `getTimersByExternalId` returns all active timers that carry it.

== Upgrading

The `EXTERNAL_ID` column is nullable, and existing applications that use a plain `TimerConfig` keep working unchanged: their timers simply have a `NULL` external identifier.

For databases that already hold timers, WildFly adds the column for you. On the first start after an upgrade, the database timer persistence detects that `EXTERNAL_ID` is missing and runs an `ALTER TABLE` to add it. This means the database user configured for the timer store needs permission to alter that table.

== Under the hood

The API lives in the `jboss-ejb3-ext-api` library. In the server, the database timer persistence now includes `EXTERNAL_ID` in its `INSERT`, `UPDATE` and `SELECT` statements and queries it with a prepared statement. When you ask for timers by external identifier, the timer service also checks the active in-memory timers and any timers created in the current, not yet committed, transaction. The result is therefore complete and consistent with what your code has just done.
