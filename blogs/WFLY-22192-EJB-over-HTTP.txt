If you've ever tried to move an application that uses remote Jakarta Enterprise Beans onto OpenShift or Kubernetes, you've probably hit the same wall I did. The native Remoting protocol for Enterprise Beans is a long-lived binary connection, and the cloud is built for HTTP. Layer-7 load balancers, ingress controllers and service meshes are designed to terminate, inspect and route HTTP traffic, and they generally have no idea what to do with a Remoting connection. You can make it work for a single server if you fight the infrastructure hard enough. But the moment you add clustering, stateful beans and distributed transactions, the questions pile up. Which pod handles my transaction? What happens to an in-flight transaction when that pod restarts? How does recovery find its way back to the right place? For a long time there hasn't been one validated answer.

So we set out to build one. The short version: run your Enterprise Beans traffic over HTTP, and let the platform take care of the hard parts.

== Enterprise Beans over HTTP

The transport is Enterprise Beans over HTTP, carried by the https://github.com/wildfly/wildfly-http-client[wildfly-http-client,window="_blank"] library. HTTP is exactly what cloud networking is built to route, so instead of tunnelling a protocol the infrastructure doesn't understand, your invocations travel as something it does. Two more pieces sit on top of that transport and make it correct rather than just functional: an affinity-aware client that encodes the server's routing decisions, and a stable-identity deployment model that gives each server the durable identity transaction recovery depends on.

== Why routing has to be precise

This is the part that turns out to matter most, and it's worth a minute even if you never touch the internals.

A transaction is not a free-floating thing that any server can pick up. While it's in flight, it belongs to the specific server that started it, because that server holds its state and, if something goes wrong, its recovery log. If a later call in the same transaction lands on a _different_ pod, that pod has no idea the transaction exists, and the call fails. A normal cloud load balancer, which happily spreads requests across interchangeable replicas, is precisely the wrong tool here.

What you want instead is a load balancer that sends each request to the exact pod its transaction belongs to. Just as importantly, it should refuse the request rather than guess when that pod isn't reachable. "Route precisely, or fail fast" is the whole game. Guessing wrong doesn't just drop a request; it can corrupt a transaction. So the architecture relies on strict, token-based routing: the server decides where a request must go, the client encodes that decision, and the proxy enforces it to the letter.

== Let the operator do the wiring

You don't want to assemble all of that by hand, and the design means you shouldn't have to. When you deploy your workload through the https://github.com/wildfly/wildfly-operator[WildFly Operator,window="_blank"], it takes on the parts that are easy to get subtly wrong:

* it runs your servers as a StatefulSet with stable identities;
* it stands up a strict-routing HAProxy in front of them;
* it wires up the transaction store and recovery, so that an in-doubt transaction is completed after a crash;
* it forms the cluster using cloud-friendly discovery.

The goal we keep steering toward is a two-line story for the application developer: deploy your Enterprise Beans workloads through the operator, and use HTTP between them. Everything else — the topology, the proxy, stable identity, discovery and recovery — is the platform's job to absorb, not yours to configure.

== A set of requirements, proven by tests

This is more than a library you drop in. It is a set of requirements that describe how Jakarta Enterprise Beans must be deployed and invoked when WildFly runs in the cloud, so that behavior stays conformant with the specification. That covers affinity, transaction propagation, security identity and crash recovery. And because a set of requirements is only as trustworthy as its evidence, it comes with a conformance test suite. The suite exercises the whole architecture end to end against a real cluster and checks that the guarantees actually hold.

The recommended topology is a StatefulSet managed by the operator with a durable transaction store. It's the one we validate and stand behind today. Looser setups are possible for teams that can't use StatefulSets, or for workloads that are purely stateless, but they give up some of the guarantees. We have listed them as future work, clearly labelled, rather than quietly recommending them.

The full design, including the requirements and the topology guide, is written up as a https://github.com/wildfly/wildfly-proposals/pull/884[WildFly design proposal,window="_blank"] if you want the details behind this summary. The proposal is still under review, and so is the work behind it. This post describes where we're heading, not a feature you can download today.
