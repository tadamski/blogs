Datasource connection validation is essential for keeping a connection pool healthy. But when a validation query runs against a stale connection, it can hang, and a hung validation can hold up the whole pool, especially during background validation. JDBC drivers already support query timeouts, but a driver-level timeout affects every query, including legitimate long-running operations that must be allowed to finish.

WildFly 43 solves this with a dedicated `validation-timeout-seconds` attribute for datasources. You can now enforce a short timeout on validation checks only, without touching the timeouts of your normal queries.

== The problem

When a connection goes stale (network interruption, database restart, idle timeout), many JDBC drivers will block on a validation attempt for a very long time. This causes two kinds of trouble:

* *Background validation* can stall while it scans for invalid connections. A single stale connection can hold up validation of the whole pool until the attempt finally times out or fails.
* *Validate-on-match* delays connection acquisition. Even when the pool has valid connections, finding one may mean waiting out the hang on each stale connection encountered first.

Setting `query-timeout` is not a workable fix, because it applies to all queries, including business operations that legitimately take minutes or hours. A validation query, by contrast, should answer almost instantly. If it doesn't, the connection is broken.

== How to use it

The new `validation-timeout-seconds` attribute is available for both regular and XA datasources. The value is in seconds and defaults to `0`, which means no timeout. When it is set, the timeout is applied to both background validation and validate-on-match.

=== Using the CLI

[source]
----
/subsystem=datasources/data-source=ExampleDS:write-attribute(name=validation-timeout-seconds, value=2)
----

For an XA datasource, use the same attribute on the `xa-data-source` resource:

[source]
----
/subsystem=datasources/xa-data-source=ExampleXADS:write-attribute(name=validation-timeout-seconds, value=2)
----

=== Using a `-ds.xml` deployment descriptor

The attribute is also available in the `<timeout>` section:

[source,xml]
----
<datasource jndi-name="java:jboss/datasources/ExampleDS" pool-name="ExampleDS">
    <connection-url>jdbc:h2:mem:test</connection-url>
    <driver>h2</driver>
    <timeout>
        <validation-timeout-seconds>2</validation-timeout-seconds>
    </timeout>
    <validation>
        <valid-connection-checker class-name="org.jboss.jca.adapters.jdbc.extensions.novendor.JDBC4ValidConnectionChecker"/>
        <background-validation>true</background-validation>
    </validation>
</datasource>
----

A value of 2–5 seconds is a reasonable starting point for most environments.

== Which connection checkers support it

The timeout is handed to the datasource's connection checker through a new `setTimeout(int)` method on IronJacamar's `ValidConnectionChecker` interface. The built-in checkers behave as follows:

* `JDBC4ValidConnectionChecker` (and the Oracle and "good for seconds" checkers that extend it) calls `Connection.isValid(timeout)`.
* `CheckValidConnectionSQL` (and the MySQL, PostgreSQL, DB2, Microsoft SQL Server and Sybase checkers that extend it) sets the timeout on the validation statement with `Statement.setQueryTimeout()`.
* `MySQLReplicationValidConnectionChecker` applies the timeout to both of its validation paths.
* `OracleLegacyValidConnectionChecker` ignores the value, because Oracle's `pingDatabase` API has no timeout parameter.

IMPORTANT: A checker that does not implement `setTimeout(int)` — this includes custom checkers written before this change — cannot accept the value. If you configure `validation-timeout-seconds` for such a checker, WildFly logs the failure and disables connection validation for that datasource. If you use a custom `ValidConnectionChecker`, implement `setTimeout(int)` before you enable the new attribute.

== Under the hood

The feature spans IronJacamar and WildFly's datasources subsystem. IronJacamar parses the new setting, stores it on the managed connection factory, and, if it is non-zero, passes it to the configured checker before validating a connection. The datasources subsystem exposes it as a new management attribute. When a domain includes hosts running older servers, a defined `validation-timeout-seconds` value is rejected for them, while an undefined value is simply ignored.
