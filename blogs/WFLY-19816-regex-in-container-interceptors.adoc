WildFly offers two ways to intercept Jakarta Enterprise Beans invocations. Jakarta Interceptors are defined in `ejb-jar.xml` or with annotations and are mandated by the specification. Container interceptors are specific to WildFly and are defined in `jboss-ejb3.xml`. They run before the container's own invocation processing, such as security context propagation and transaction management, which makes them a good fit for cross-cutting concerns like auditing that must see every call first.

Both kinds of interceptor use an `ejb-name` element to say which beans a binding applies to. Jakarta Interceptors have long supported regular expressions in that element: set the `allow-ejb-name-regex` attribute of the `ejb3` subsystem to `true`, and one binding can match many beans. Container interceptors, however, always treated `ejb-name` as a literal string, so the setting had no effect on them.

Starting with WildFly 43, container interceptors honour `allow-ejb-name-regex` too.

== How to use it

Enable regular expressions in the `ejb3` subsystem, exactly as you would for Jakarta Interceptors:

[source]
----
/subsystem=ejb3:write-attribute(name=allow-ejb-name-regex, value=true)
----

Then use a regular expression in a container interceptor binding in your `META-INF/jboss-ejb3.xml`:

[source,xml]
----
<jboss xmlns="http://www.jboss.com/xml/ns/javaee"
       xmlns:jee="http://java.sun.com/xml/ns/javaee"
       xmlns:ci="urn:container-interceptors:1.0">
    <jee:assembly-descriptor>
        <ci:container-interceptors>
            <jee:interceptor-binding>
                <ejb-name>.*Service</ejb-name>
                <interceptor-class>com.example.AuditInterceptor</interceptor-class>
            </jee:interceptor-binding>
        </ci:container-interceptors>
    </jee:assembly-descriptor>
</jboss>
----

This applies `AuditInterceptor` to every bean in the deployment whose name matches `.*Service`. The pattern has to match the whole bean name, so `.*Service` selects `OrderService` but not `OrderServiceBean`. The special value `*` keeps its existing meaning of "all beans", regardless of the regex setting.

Nothing changes for existing deployments. With `allow-ejb-name-regex` left at its default of `false`, `ejb-name` is still treated as a literal name. If regular expressions are enabled and a value is not a valid Java regular expression, WildFly rejects the deployment with an error that identifies the offending pattern.

== Under the hood

The change is small because it reuses existing infrastructure. When regular expressions are allowed, the `ejb-name` of a container interceptor binding is compiled as a `java.util.regex.Pattern` and matched against the names of the Jakarta Enterprise Beans in the deployment, using the same logic that Jakarta Interceptors already use. There are no new attributes or elements to learn.
